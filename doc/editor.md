# Editor Requirements

**Status:** Draft requirements for the SpecUX editor; not normative.

The browser editor prototype is at the repository root; its sample project is in `specux/`. The prototype is exploratory and is used to try ideas and evaluate the intended experience. Its implementation choices and limitations are not requirements for the final product. This document describes the target product and should evolve as those requirements are refined.

Screen-editor-specific behavior is maintained separately in the [Screen Editor Requirements](screen-editor-requirements.md). Update that document when Screen-editor requirements change; this document remains the broader, non-normative product direction.

| ID | Target requirement |
|---|---|
| ED-001 | Open a SpecUX project and resolve its Screens, reusable Material STML files, Theme, optional project- and Screen-level Markdown behavior specs, and Material resources. Screen composition uses Material references with placement-specific transforms. |
| ED-002 | Validate project structure and references on load, and make missing or invalid artifacts clear to the user. |
| ED-003 | Provide a selectable Project Overview with summaries of its Screens, reusable Materials, Theme, and attached behavior specs. Show a collapsible file tree for project configuration, Materials, and Screen files. Open supported files in their corresponding Studio views and keep selection consistent. Allow existing Material templates to be edited and placed again from the project tree or selected placement. |
| ED-004 | Keep the details inspector focused on the current selection: Project, project-level behavior spec, Theme, Screen, or selected Material. Do not mix unrelated entity details. |
| ED-005 | Render each Screen as a canvas of independent, visual-only Material instances. Support reusable Label and Button templates defined by single-root HTML in STML files. Give each instance its own variable overrides, absolute canvas coordinates, size, rotation, and transform scale. Support named visual states as sparse overrides of placement visibility, Material attributes, transforms, and layer visibility. Preserve project Theme tokens and contain project content within the preview. |
| ED-006 | Let users open and edit a reusable Material's STML markup and metadata. Provide direct canvas controls and inspector fields to move, resize by X/Y dimensions or transform scale, and rotate each placement independently. |
| ED-007 | Validate Material front matter, single-root HTML markup, local resources, and numeric placement transforms; report invalid values instead of silently substituting content or dimensions. |
| ED-008 | Edit Screen metadata, reusable Material files, placement transforms, and Theme values. Materials are visual only and do not accept input or execute actions. |
| ED-009 | Apply project Theme tokens as CSS custom properties to rendered project previews. Keep Theme configuration limited to token values so it cannot change Material structure or editor styles. |
| ED-010 | Support project- and Screen-level Markdown behavior specs. Materials are visual only and do not have individual behavior specs. Require OpenSpec's structured Purpose, Requirements, and scenario format; treat specs as declarative behavior contracts, not executable actions or implementation plans. Use explicit `specux://screen/.../screen.yml` links to drive Screen, state, and placement previews; attach Element specs through their matching placement link rather than YAML front matter. |
| ED-011 | Let a human inspect rendered results and record a review outcome for the relevant Screen, Material, or Theme. |
| ED-012 | Persist ordinary edits automatically through a Node.js server that validates and writes project files; do not require or expose a manual Save action. The frontend does not write to the filesystem directly. Confine writes to the opened project root and report failures without clearing pending edits. |
| ED-013 | Preserve project information when reading and writing files, including unknown fields or content the editor does not support. Never silently discard data or break compatibility. |
| ED-014 | Provide reliable error feedback for invalid values, unsupported features, missing files, and failed saves; do not silently substitute success-shaped results. |
| ED-015 | Support undo and recovery for user edits, including explicit resolution of external-file conflicts; do not expose a global reset-from-files action. |
| ED-016 | Let users position, resize, rotate, and remove Material placements directly on the canvas. Keep shared Material content in reusable STML files; do not turn Materials into layout groups or slot containers. |
| ED-017 | Create a Screen with a unique project ID and file, add it to the project manifest, and initialize it with an empty `materials` list. |
| ED-018 | Expose machine-readable context on each Material placement so browser inspection and automation can identify its owning Screen, placement ID, referenced Material file, and visible text or label. |
| ED-019 | Expose the current Screen ID and name on each Screen manifest file-tree entry and on major Screen-view containers, including the workspace context, main canvas, stage, and preview. Use the `data-specux-screen-id` and `data-specux-screen-name` attributes defined in `screen.md`. |
| ED-020 | Adapt the Studio interface to the operating system's light or dark color scheme, independently of the active project Theme, and respond to system preference changes while open. |
| ED-021 | Support one optional project-level OpenSpec-formatted behavior spec referenced by `project.spec` for requirements that apply across multiple Screens or throughout the project. Let users create or edit it from the Project Overview and persist a new file and manifest reference together only when its draft changes; discard an unchanged new draft when the user leaves it. Do not use it for Screen-specific behavior. |
| ED-022 | Let each Screen define named visual states as sparse overrides over Default, require a description for every non-default state, and switch between them without altering Default values. In named states, allow editing placement visibility, Material attributes, transforms, and layer visibility; persist edits through the normal save flow. Restrict structural edits to Default, and let newly added Default placements inherit into existing states. Require each non-default state to be referenced with `SHOW <state-id>` after `THEN` in the Screen-level spec. Allow selecting hidden Materials from the Screen material list. |
| ED-023 | Provide a searchable Screen selector at the top of the file explorer, with available Screens searchable by name or ID. Selecting a Screen opens it, expands its path, and selects its `screen.yml` file. |
| ED-024 | Represent editor and canvas context in the URL. Add a browser history entry only when the displayed Screen changes; replace the current URL for same-Screen editor, mode, selection, or target changes. Back and Forward must restore the full context without adding entries during restoration. |
| ED-025 | Define reusable Materials as `.stml` templates under `materials/`, each with front matter variable mappings and one HTML root element. Store a Material reference and instance-specific variable overrides, ID, absolute position, size, rotation, transform scale, and visibility in Screen YAML; store Screen State visual overrides sparsely in `preview-states`. |
| ED-026 | Provide annotation tools for the active editor view, including Screen, Spec, Material, Theme, workflow, Markdown, and source previews. Keep editor-specific selection, editing, and preview behavior available outside annotation interactions. |
| ED-027 | Let the CLI capture the visible active editor surface from the connected browser for AI communication, including unsaved edits. Include visible annotation marks in the PNG and return their structured data with the editor context; do not persist captures in project files. |
| ED-028 | Provide pen, circle, rectangle, arrow, highlight, and note tools with undo, redo, and clear actions. Selecting a tool enters annotation mode. Keep the accessible Exit control visible at all times and disabled outside annotation mode. Keep the annotation tools and actions together when a responsive toolbar overflows. |
| ED-029 | Give each preview its own annotation layer and store marks in that preview's pixel coordinates. Size the annotation canvas to at least the visible preview viewport and extend it to the full content bounds when content is larger. Allow scrolling only on axes where content exceeds the viewport. Scrolling, zooming, and resizing must not move marks relative to preview content. Screen-preview marks use Screen-canvas coordinates; other editor views publish the preview identity and full-content coordinates. |
| ED-030 | Make source views annotatable without changing their text. Use a non-editing text mirror or overlay, synchronize its scroll position with the source editor in both directions, and preserve selected text visibly when focus moves to annotation controls. |
| ED-031 | In the Theme editor, annotation-mode pointer input on the annotation overlay creates marks rather than invoking Theme color picking. Outside annotation mode, preserve Theme color picking; annotations must not select or change Screen placements. |
| ED-032 | Keep annotation overlays within the active editor's stacking context, above preview content but below project-structure and Properties hover panels and edge triggers. Navigation must stay visible and pointer-accessible, and a panel must not auto-hide while the pointer remains over it. |
| ED-033 | Keep annotations transient and separate from project artifacts. Screen marks are structured vector data with placement and Material identity where available; annotations in other editor views are active-file and preview-specific AI context only. Whenever the active file changes, clear annotations before loading the next file; do not restore annotations when returning to a file. Keep project edit history independent of navigation and active-file changes. Never write annotations to project files or use non-Screen marks as Screen-render input. |
| ED-034 | Let users select the Material preview and resize its width and height in X/Y mode using preview handles; do not offer rotation or transform scaling. Apply the dimensions live while dragging and update the STML `preview-size` property on pointer release. If the property is absent, use the type's default preview size. Preview sizing must not change Screen placement sizes. |
| ED-035 | Open Material files in a resizable vertical Split view by default, with the preview above the STML source editor. Center the Material in a clipped, pannable canvas with pixel rulers, the Screen editor's subtle dot-grid system anchored at the canvas origin, and zoom controls. Keep the Material's top-left at canvas coordinate (0, 0) fixed relative to the canvas while zooming; zoom scales outward from that origin, while panning moves the canvas origin without changing Material dimensions. Material preview resizing continues to update its unscaled `preview-size` dimensions. Keep the preview selected until the user selects empty canvas; Escape returns to the Screen workspace. |

## Superseded Target Page Layout

The earlier proposed persistent file-explorer/three-column layout is superseded by the Screen-centered workspace described in the [Screen Editor Requirements](screen-editor-requirements.md). The current layout keeps the Screen canvas primary in Screen, Workflow, Spec, and Theme modes, uses a Material selector and project-file view in the left panel, contextual Details on the right, and a bottom dock for Workflow and Spec views. Material authoring uses its own preview/source workspace. Keep the Project Overview available; do not treat the earlier column arrangement as a requirement.

## Prototype Context

The current editor uses a local Node.js server to serve the `specux/` example project and validate file writes. The top toolbar selects Screens; the left panel provides Material selection and project files; the right Details pane exposes contextual editing; and Workflow and Spec views use the bottom dock while the Screen remains visible. Material files open in a dedicated preview/source workspace. Ordinary valid edits autosave, a compact status indicator shows pending, saving, saved, or error state, and one session-only project history provides undo and redo across editor types. The server only allows supported edits under the example project. Review-state persistence remains an open design decision.

When a behavior spec is open, selecting a Material only highlights it in the preview; Materials have no individual behavior specs.

Editor and canvas context are reflected in the URL. Browser history adds an entry only when the displayed Screen changes; changes to editor, mode, selection, or target on the same Screen replace the current entry.
